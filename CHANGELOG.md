# Changelog

All notable changes to this package are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the package follows
[semantic versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Fixed

- A saved card could be charged after a wallet the payer opened had gone quiet. The sheet
  lets go 15 seconds after the payer comes back with no charge started, and that hold now
  releases the card form only: a saved card is charged on an invoice of its own, so a slow
  wallet charge landing after it would be a second payment for the same order, which no
  per-invoice rule can refuse. The card form pays this invoice and stays open.
- A checkout opened without `expectedInvoiceId` took a return link for any invoice. It now
  binds to the invoice its own `checkout_url` names, which `/init` always puts there, so a
  link for another invoice is passed over and the checkout goes on waiting for its own. This
  covers `GetPayInCheckout.open`, `GetPayInCheckout.saveCard` and `GetPayInCheckoutView`;
  the payment sheet already bound to its session's invoice.

## 0.2.0

The first version on pub.dev. Version 0.1.0 was tagged in the repository but never
published, so this entry lists everything that changed since that tag.

### Added

- `CheckoutResultCode.outcomeUnknown`, for a charge that went out and whose answer never
  came back — the network went, the page died, the payer closed the sheet mid-charge, your
  own server threw after it had called — and for an invoice PayLink says is already paid.
  The one result that is neither a payment nor a refusal: read the invoice, and never take
  payment again on it. `PaymentSheetStrings.outcomeUnknown` is what the payer is told then;
  never "try another card", because the card may already have been charged.
- `closedByAppMessage`: a checkout screen your app takes away in its own code settles as
  `cancelled` with it, or with `closedByUnmountMessage` when the provider went with it, so
  `open()` always returns and the next checkout can open.
- `GetPayInCheckoutView.onPageLoaded`, which tells a failure that may follow a charge from
  one before the checkout ever loaded.
- `FieldsFailure.alreadyPaid`, `notPayable`, `expired` and `consentRequired`, so every code
  PayLink's fields send about a payment has a name, and `FieldsFailure.pageOutdated` for a
  card page older than the package.
- `WalletSurface.onCharging`, which says a wallet charge is out; `onChargingAfterLeaving`,
  which says it was marked as the button left the screen; `onUnavailable`, which says
  the page cannot show the wallet at all; and `onChallenge`, which says the issuer's 3-D
  Secure check is up on the wallet's page, or has gone.
- `FieldsPayment.attempt` and `FieldsError.attempt`, the code that ties an answer or a
  failure to the charge it belongs to.
- `CardFieldsController.onRefused`, one line for each message the card box refused and why.

### Changed

- `GetPayInPaymentSheet` is opened with `GetPayInPaymentSheet.show` and has no public
  constructor. The sheet ends by closing its own route, so placed on a screen of your own it
  would close that screen, and nobody would receive the result.
- The card page you host is generated by this package: generate it again and upload the new
  copy with every update. The sheet hands the page a key when it starts it and takes only
  messages that carry the key back, because anything the page frames can post to it. A page
  from an older version sends no key; the sheet notices before the payer can pay and hands
  them to the hosted checkout with `page_outdated`.
- The card page loads an SDK its own link names only from a PayLink it was generated for:
  anyone can send a payer a link to it. Name every PayLink whose wallet payments it takes,
  with `buildFieldsPageHtml(otherSdkUrls:)` or as more hosts to `tool/write_fields_page.dart`.
- A checkout is settled only by a return link that arrives while it is watching. The package
  listens for deep links once, as `GetPayInProvider` mounts, and a link that reaches the app
  with no checkout waiting for one is dropped. Neither source `app_links` offers is tied to a
  live checkout, so the ordering is decided here rather than taken from it. A dropped link,
  and one that settled a checkout, is refused for ten minutes after. See
  [Setup](doc/setup.md) if your app reads links of its own.
- Bound to `expectedInvoiceId`, every checkout (the browser sheet, the in-app screen and the
  wallet button) passes over a return link that names another invoice, or none, and goes on
  waiting for its own; before, the in-app screen and the wallet took a "not paid" in it as
  the answer. `GetPayInCheckoutView.onPassedOver` and
  `CheckoutNavigationHandler.onPassedOver` say when. A link that names its invoice is
  taken even when its result cannot be read. A checkout that closes with no answer after
  passing over a link settles `outcomeUnknown`, and so does a card save.
- The payment sheet holds every result to the session's invoice when `expectedInvoiceId` is
  left out. A value that is not an invoice id, a `returnUrl` with no scheme, or a session
  whose `checkout_url` is not a web link makes `show()` throw a `GetPayInConfigError` before
  the sheet opens.
- `onDiagnostic` says why the card box refused a message or handed the payer over. Blocked
  links and dropped return links are logged in debug builds only, without what they carried.
- `formatAmount` reads its amount in hundredths whatever the currency, which is how PayLink
  keeps and charges every amount. The pay button showed ¥2,500 as ¥250,000, and 97.42 JOD as
  9.742 JOD.
- What `chargeSavedCard` returns is held to the same rule as every other claim of payment: a
  `paid` naming an invoice status other than `PAID` is `notPaid`. A charge on a token makes
  its own invoice, so it is not held to `expectedInvoiceId`.
- The one-checkout-at-a-time guard covers the payment sheet too, and the sheet lends its
  place to the one checkout `chargeSavedCard` opens for an issuer's challenge.
- A return link with a bracket or a control character in a field name is unreadable. A
  server may read such a name as one of the link's fields, and the app and a server checking
  the link's signature must read the same values.
- In the app's own screen, a page that fails after the checkout has loaded is drawn over the
  checkout, which stays loaded underneath. From then on the checkout settles `notPaid` with
  `outcomeUnknown` however it goes without an answer: the payer's close, your app taking the
  screen away, or the provider going. The default texts never ask the payer to try again, or
  say that nothing was charged.
- Checkout links and server errors are written to the log in debug builds only.
- The docs no longer say a `cancelled` checkout means the payer did not pay, ask for
  `android:launchMode="singleTop"` and say why `singleTask` is wrong, and agree that the
  payment sheet can take a sale that also keeps the card.

### Fixed

Every fix here closes a way a payer could be invited to pay a second time for a card that
may already have been charged, or a way a payment that went through was reported otherwise.

- Nothing in flight is reported as `cancelled`. From the tap on Pay until the answer, while
  your server charges a saved card, and from the payer opening the wallet until it answers,
  the payment sheet refuses a swipe, a tap outside and Android Back, shuts every other way to
  pay, and keeps one close, which settles `outcomeUnknown`. The wallet counts as opened when
  the app goes to the background within 10 seconds of a touch on its button. A wallet that
  starts no charge within 15 seconds of the payer coming back frees the sheet again, and
  closing after it still settles `outcomeUnknown`.
- A wallet payment that gets the issuer's 3-D Secure check gives the check the whole sheet,
  as a card's does, and holds the sheet while it is up. It was drawn inside the wallet's
  button-high row, where the payer could not answer it. The card page changed with it:
  generate it again and upload the new copy.
- The wallet button's page may go only to your registered origin, PayLink's own pages and
  the return link, as the card box's may go only to your origin. It could go to any web
  page, which could then hand back a "paid" for the invoice.
- A `GetPayInProvider` that goes while its checkout screen stays, as one inside a router
  shell can, takes the screen away with it. The screen stayed, and its close button no
  longer reached anything.
- A `GetPayInCheckoutView` given a new checkout ignores the web view it replaced. A return
  link from the old page could end the new checkout with the old one's answer.
- A wallet charge marked after its button left the screen, or while the payer was in another
  wallet, makes whatever the sheet reports next `outcomeUnknown`, and the sheet no longer
  frees itself for a second payment when that wallet's hold ends.
- An error the page could not name, arriving after the charge had gone out, handed the payer
  to the hosted checkout. Nothing falls back once a charge is out.
- A card form that fails while another payment is in flight waits for that payment to end
  before it hands the payer over, and after a wallet that never answered it settles
  `outcomeUnknown` instead. PayLink saying the invoice is already paid waits the same way, so
  the wallet charge that paid it is reported as paid.
- A late failure of one card charge could end the next one, and an error the SDK reported on
  its own could end whatever charge was running. Each charge's failure now carries that
  charge's own code.
- A card page that could not be reached could leave the sheet waiting for an answer that
  would never come. It now ends the attempt as one that cannot run. While the page loads
  again, Pay is off until its fields are back.
- A card page that did not load left an empty card box with Pay off. It now hands the payer
  over. A wallet that cannot be shown, its page included, left an empty row. It is taken
  away, and the log says why.
- A saved card's charge that outlasted the sheet could open its bank step over a checkout
  the app opened afterwards. It can open one only while its own sheet is open.
- Unticking the box that keeps the card just before Pay sent the payer to the hosted
  checkout. They are asked to tick it again on the same form.
- The reason for a decline stayed on screen during the next charge. It is cleared on Pay.
- A payer whose wallet payment was declined could try again, and the second answer went
  nowhere. The wallet is rebuilt after a decline.
- An exception from `chargeSavedCard` offered the payer another card. The sheet settles with
  `outcomeUnknown` instead.
- On Android, an `intent:` link from a bank's step opens the app it names, under the same
  rules as any other link, or its web page (`browser_fallback_url`) when no app takes it. A
  fallback that cannot be decoded is shown as a link the phone could not open, and the
  fallback page loads only into the checkout it came from.
- On iPhone, a load the web view only cancelled, as one bank redirect replaces another, no
  longer interrupts the checkout.
- On a phone with a notch, the payment sheet stays below the status bar with the keyboard up
  or down, and a 3-D Secure challenge fits whole above the keyboard.

## 0.1.0

First release: the Flutter port of
[`@getpayin/expo-checkout`](https://www.npmjs.com/package/@getpayin/expo-checkout), with the
same checkout, the same return-link rules and the same security model.

### Added

- `GetPayInCheckout.open`, `presentationFor` and `busy`.
- `GetPayInProvider`, which presents the checkout as a full-screen route on the app's own
  `Navigator`, so the system back button closes it.
- `GetPayInCheckoutView`, for putting the checkout in a screen of your own.
- `declareHostAppSchemes`, which replaces the Expo package's reading of `app.json`: Flutter
  has no app config to read at runtime.
- `PaymentReturnRedirect`, for keeping `go_router` from opening the return link as a route.
- Google Pay in the app's own screen through
  `AndroidWebViewController.setPaymentRequestEnabled`, applied before the page loads.
- The browser-sheet presentation on `url_launcher`, with the sheet's dismissal read from the
  app's own lifecycle and a grace period for a return link that races it.
- `GetPayInPaymentSheet`: the same payment taken on a sheet in your own app, with a wallet
  button, the payer's saved cards, a card form and one pay button, running on PayLink's
  hosted card fields. The card number and security code are still rendered by the gateway,
  on a page you host at your registered origin; everything around them is Flutter. See
  [The payment sheet](doc/payment-sheet.md).
- `PayLinkFieldsSession`, `FieldsFailure`, `CardFieldsController`, `WalletSurface`,
  `buildFieldsPageHtml` and the `FieldsEvent` family, so a different sheet can be built from
  the same pieces.
- `CardFieldsSnapshot` and `applyFieldsEvent`: what the card box knows is a value, and what
  an event means to it is a pure function over that value.
- `CheckoutResultCode.checkoutUnavailable`, for a sheet that could not be shown at all with
  the fallback to the hosted checkout turned off. Nothing was charged and nothing was
  declined.
- `GetPayInCheckout.saveCard`: vault a card through a hosted tokenization run, read as a
  card save rather than as a payment. A verification authorizes one unit, vaults the card
  and releases the hold, so its invoice ends `VOIDED` and the payment rules would have
  called every successful save a failure. `CardSaveResult` says `saved`, `notSaved` or
  `cancelled`, and carries the verification's own state. The token is not on the return link
  and never reaches the app; it arrives with the `card_token.created` webhook. See
  [Saving a card](doc/saving-a-card.md).
- `invoiceIdInCheckoutUrl`, which reads the invoice id out of a `checkout_url` or
  `tokenization_url` so a run can be bound to its own result.
- `readReturnClaim`, the reading of a return link before any rule about what it may mean,
  which is what lets a card save and a payment share one parser.

### Notes

- The frame rule holds on both platforms here, not iOS only: `webview_flutter` reports
  whether a navigation came from the main frame on Android as well.
- `expectedInvoiceId: null` means "no invoice to bind to". Dart cannot tell that apart from
  a field your server left out of its JSON, so make your server always send the invoice id.
